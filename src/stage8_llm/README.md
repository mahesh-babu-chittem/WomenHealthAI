# 🧠 Stage 8 — LLM-Based Personalized Health Guidance

> **Purpose:** Convert structured resilience predictions and personalized intervention recommendations into concise, patient-friendly reproductive health guidance using a locally hosted Llama-3 model.

Stage 8 represents the final communication layer of the WomenHealthAI framework.

It does not independently predict RHRS, perform forecasting, or determine clinical diagnoses.

Instead, it consumes the structured outputs generated by Stage 7 and converts them into natural-language health guidance.

The Stage 8 guidance is grounded in the structured RHRS profile, risk category, and intervention recommendations supplied by Stage 7; the LLM does not reinterpret or independently generate the underlying analytical results.

---

The Stage 8 workflow is:

    Stage 7 Intervention Recommendations
                    │
                    ▼

                    │
                    ▼
             Risk Category
                    │

        Personalized Interventions
                    │
                    ▼
              Llama-3
                    │
                    ▼
        Patient-Friendly Report
                    │
                    ▼

Stage 8 therefore functions as a **natural-language communication layer** over the structured decision-support outputs generated by the preceding stages.

The manuscript describes the overall WomenHealthAI pipeline as sequentially transforming multimodal observations into RHRS, forecasting future resilience, explaining influential factors, generating intervention targets, and finally communicating the resulting information through LLM-based guidance.

# 4️⃣ Local Model Execution

The implementation uses Ollama rather than a remote API.

This provides a locally executed LLM generation workflow.

The basic architecture is:

    Python
      │
      ▼
    Ollama
      │
      ▼
    llama3:latest
      │
      ▼
    Generated Report

The implementation therefore does not require a cloud-based LLM API for report generation.

# 5️⃣ Prompt Construction

For every participant, a structured prompt is constructed containing:

    Patient Profile

    RHRS:
        participant RHRS

    Risk Category:
        participant risk category

    Interventions:
        Stage 7 intervention recommendations

The prompt then instructs the model to generate four sections:

    1. Health Summary
    2. Main Resilience Concerns
    3. Personalized Recommendations
    4. Monitoring Advice

The current implementation explicitly specifies these four sections.

---

# 6️⃣ Prompt Constraints

The LLM is instructed to follow the following requirements:

    • Professional clinical tone
    • Easy to understand
    • Maximum 250 words
    • Do not mention AI
    • Do not provide medical diagnosis

These constraints are directly encoded in the prompt used by `ollama_guidance_generator.py`. :chatgpt-content-reference{index="1"}

The prompt therefore attempts to constrain the generated output toward concise, accessible, non-diagnostic health guidance.

---

# 7️⃣ Report Generation

The main generation loop iterates through every participant in the Stage 7 intervention file.

For each participant:

    1. Read RHRS
    2. Read risk category
    3. Read intervention recommendations
    4. Construct prompt
    5. Send prompt to Llama-3
    6. Extract generated response
    7. Save report

The model response is obtained from:

    response["message"]["content"]

and saved as a participant-specific text file. :chatgpt-content-reference{index="2"}

---

# 8️⃣ Participant-Level Output

Each participant receives an individual report:

    patient_<ParticipantID>.txt

For example:

    patient_1.txt
    patient_2.txt
    patient_3.txt

The participant identifier is obtained directly from the Stage 7 intervention file.

This makes the generated guidance traceable to the corresponding structured intervention record. These participant-specific reports are analysis artifacts intended for authorized use and should not be included in a public release unless participant-level sharing has been explicitly approved.

# 🔟 Stage 8 Quality Evaluation

### Script

    llm_evaluation.py

The evaluation script performs three principal evaluations:

    1. Word Count
    2. Readability
    3. Guidance Fidelity Score (GFS)

The evaluation results are saved as:

    results/stage8_llm/llm_evaluation.csv

---

# 1️⃣1️⃣ Word Count

The generated report is tokenized using:

    report.split()

and the number of resulting words is recorded.

The resulting metric is:

    WordCount

This measures whether generated reports remain concise.

The manuscript reports an average generated report length of:

    230.88 words

which is below the 250-word prompt constraint. :chatgpt-content-reference{index="4"}

---

# 1️⃣2️⃣ Readability

Readability is measured using:

    textstat.flesch_reading_ease()

The resulting value is stored as:

    Readability

The manuscript reports:

    Readability Score = 13.35

for the generated reports. :chatgpt-content-reference{index="5"}

The score is used as a language-level readability indicator rather than as a clinical quality metric.

---

# 1️⃣3️⃣ Guidance Fidelity Score

The primary semantic consistency metric is:

    Guidance Fidelity Score (GFS)

The manuscript defines GFS as:

        |C|
    GFS = ───
        |T|

where:

    C = number of intervention concepts covered
    T = total expected intervention concepts

This definition appears as Equation (21) in the manuscript. :chatgpt-content-reference{index="6"}

---

# 1️⃣4️⃣ Current GFS Implementation

The current implementation derives expected intervention concepts from the Stage 7 intervention text.

It checks for the following concept categories:

    hormonal
    psychological
    metabolic
    behavioral
    symptom
    resilience

The evaluator converts both the intervention text and generated report to lowercase and checks whether each expected concept occurs in the generated report.

For example:

    "hormonal" in report_text

is used to determine whether the hormonal intervention concept is present.

The same procedure is applied to the other expected concepts.

---

# 1️⃣5️⃣ GFS Calculation

The implementation calculates:

    covered / len(expected)

when intervention concepts are available.

If there are no expected intervention concepts, the implementation assigns:

    GFS = 1.0

The resulting participant-level GFS is stored in:

    llm_evaluation.csv

The relevant implementation is contained in `llm_evaluation.py`. :chatgpt-content-reference{index="7"}

---

# 1️⃣6️⃣ Aggregate Evaluation

After participant-level evaluation, the script computes the mean of:

    WordCount
    Readability
    GFS

This provides the overall Stage 8 evaluation summary. :chatgpt-content-reference{index="8"}

# 2️⃣7️⃣ Important Evaluation Limitation

The current GFS implementation is a **concept-coverage metric**.

It checks whether expected intervention keywords occur in the generated report.

Therefore:

    GFS = 1.0

means that all expected intervention concepts were detected by the implemented lexical matching procedure.

It does not independently establish:

    • Clinical correctness
    • Medical safety
    • Factual correctness
    • Recommendation appropriateness
    • Hallucination absence
    • Linguistic quality
    • Patient satisfaction

This distinction is important when interpreting the reported GFS result.

---

# 2️⃣8️⃣ Why GFS Is Used

The purpose of GFS is to measure whether the LLM preserves the intervention concepts supplied by the structured intervention engine.

Conceptually:

    Structured Intervention
              │
              ▼
             LLM
              │
              ▼
       Generated Report
              │
              ▼
     Intervention Concepts
              │
              ▼
             GFS

A high GFS therefore indicates strong coverage of the expected intervention concepts under the defined evaluation procedure.

# 2️⃣9️⃣ Safety Boundary

The LLM prompt explicitly instructs the model:

    Do not provide medical diagnosis.

This is important because Stage 8 is designed as a health-guidance communication layer rather than a diagnostic system.

The generated text should therefore communicate the structured intervention information without converting the model into an autonomous diagnostic component. The LLM output is a communication layer over the upstream decision-support results, not an independent clinical assessment.

# 3️⃣0️⃣ Uncertainty Consideration

The manuscript explicitly recognizes an uncertainty-propagation limitation.

Intervention priorities can depend on predicted RHRS values rather than directly observed values, meaning forecasting uncertainty may propagate into downstream recommendations.

The manuscript therefore identifies:

    • Explicit uncertainty modeling
    • Uncertainty-aware intervention strategies

as future research directions. :chatgpt-content-reference{index="15"}

Stage 8 should consequently be interpreted as communicating downstream analytical outputs rather than independently validating the certainty of those outputs.
